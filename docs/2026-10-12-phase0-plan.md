## 2. Findings that bear on the architecture

**F1 — Omarchy already tried a smart filter on this exact PipeWire version and it failed.**
`$OMARCHY_PATH/default/audio/tunings/dell-xps-2026/filter-chain.conf` says:
> "A smart filter is the better shape … but on PipeWire 1.6.8 / WirePlumber 0.5.15 this graph loads and links
> correctly as a smart filter and then passes audio through unprocessed: its controls are present and
> mpv -> filter -> sink links are made, yet the filter's input monitor and the speaker sink's monitor measure
> identically. Revisit when that is understood."

`omarchy-audio-tuning` also removes a stale `wireplumber.conf.d/90-omarchy-speaker-tuning.conf` from that earlier
smart-filter attempt. They ship a plain filter-chain `Audio/Sink`, hosted as a child `pipewire -c omarchy-speaker-tuning.conf`
under a systemd user unit (`PartOf=pipewire.service`), not loaded into the daemon. That hosting pattern is useful for spike C.
→ Spike A must prove **with measurement**, not by ear, that the smart filter actually processes audio.

**F2 — A smart filter will show up as a selectable output in Omarchy's audio panel.**
`plugins/panels/audio/Panel.qml:23-30` lists every node with `isSink && !isStream`. The availability filter
(`omarchy-audio-sink-availability`) only hides the sink that the Omarchy speaker tuning sits in front of.
A filter sink has no ports, so it counts as available. WirePlumber never picks a smart filter as the *best* default
(`find-best-default-node.lua:57`). But if the user picks it in the panel, `Pipewire.preferredDefaultAudioSink` makes it the
configured default, which breaks the "filter never becomes the default sink" rule. No plugin API can hide it without
editing `$OMARCHY_PATH`.

**F3 — Omarchy's volume controls always act on the physical sink.**
The volume keys (`omarchy-audio-output-volume`), the panel slider (`volumeSinkName`) and the output switcher all resolve
through any DSP sink to the physical one with `omarchy-audio-output-sink`. With a smart filter the default stays the
physical device, so the slider and keys drive the device's volume and never the filter's. A DVC built on `capture.volumes`
(the filter sink's own volume) would therefore never be touched by Omarchy's controls. For DVC, the daemon would have to
mirror the device volume into the DSP and pin the device volume, and Omarchy's OSD would then show the pinned value.
→ Spike D has to settle whether DVC is worth having on this desktop.

**F4 — Alternative path: a filter graph inside the device node.**
On PipeWire 1.6.8, every adapter node exposes `audioconvert.filter-graph.N` and `audioconvert.filter-graph.disable` in
`PropInfo`. Both `alsa_output…analog-stereo` and `bt_combined` do. WirePlumber 0.5.17 ships `scripts/node/filter-graph.lua`
(`node.filter-graph.rules`, action `create-filter-graph`), which sets those params on matching nodes. If this works, the DSP
runs inside the device sink itself:
- there is no extra node, so nothing appears in the picker (F2) and there is no routing to get wrong (§10 routing test);
- the volume keys keep working unchanged (F3);
- the F1 smart-filter failure mode does not apply;
- bypass is `audioconvert.filter-graph.disable`.

Unknowns, none documented that I could find:
- where the graph sits relative to the software volume, the resampler and the monitor ports;
- whether individual controls can be changed live, and under which param key names;
- whether LV2 loads in that context;
- what a graph replace costs, audibly;
- whether the graph survives a WirePlumber restart, and what happens when omadspd dies;
- whether it works on BT A2DP sinks.

PROMPT §5 says to challenge the architecture only with evidence, so this becomes **Spike A′**. If it holds up, I'll write an
ADR to make it the primary path and keep the smart filter as a fallback.

**F5 — OSD.** Third-party plugins cannot summon `omarchy.osd` through their facade. `shell.qml` `pluginCloneMaySummon` only
allows clones of audio, media and monitor. The daemon and CLI can still show it with `omarchy osd -m "Preset: Warm V"`, which
runs `omarchy-shell -q osd show '<json>'`. Payload: `icon`, `message`, `value`, `max`, `progressText`, `duration`.

**F6 — Plugin manifest.** `PluginRegistry.validateManifest` only checks `schemaVersion === 1`, the required
`id`/`name`/`version`/`kinds`/`entryPoints`, safe relative entry points, `barWidget.defaultSection ∈ {left,center,right}`,
and the reserved `omarchy.*` namespace. Multi-kind `["service","bar-widget"]` is what built-in `omarchy.media` uses.
A third-party plugin's `shell.serviceFor(id)` only resolves its own id (`pluginOwnsTarget`). That confirms the PROMPT §8.4
VERIFY on paper; Phase 2 confirms it at runtime.

**F7 — pipewire-rs 0.10.1** has no `Context::load_module`. It does expose `Context::as_raw_ptr() -> *mut pw_context`, so
`pw_context_load_module` is a single `unsafe` FFI call through `pipewire-sys`.

**F8 — Things specific to your setup.**
- Never capture from a BT headset mic: WirePlumber flips it to HFP, which broke `bt_combined` before. Spikes only record
  monitors of nodes they create themselves.
- The voice daemon's `pw-record` on the built-in mic must not be disturbed.
- There is no 96 kHz hardware and no USB DAC/BT right now, so 96 kHz, hotplug and BT checks wait until a device is available.

## 4. Safety model for every spike

1. **Runtime only.** Each spike runs as a foreground child `pipewire -c <repo>/spikes/<x>/host.conf`, using the minimal host
   config from `$OMARCHY_PATH/default/audio/filter-chain-host.conf`. Killing the process removes every node it created.
   A′ only does `pw-cli set-param` on a node the spike owns, and a `trap` resets it on exit. **No file is written outside the repo.**
2. **A private test sink.** Each host config also creates `omadsp_spike_out` (`support.null-audio-sink`,
   `priority.session = 0` so it can never become default). Test signals go there with an explicit
   `pw-cat --target omadsp_spike_out`, so your speakers and apps are untouched.
   Measurements record **only** that sink's monitor (or the filter's own monitor), never a microphone.
3. **Targeted smart filter.** Spike A sets `filter.smart.target = { node.name = "omadsp_spike_out" }`, so it applies only to
   streams headed for the test sink.
4. **Steps marked 👂 need you.** They play audio on your speakers (click checks while dragging) or briefly change the default
   output (the "follows default device" check). I'll ask right before each one, at low level with the limiter in place. You can
   say no and I'll record them as untested.
5. **Cleanup check after each spike.** `wpctl status` and `pw-metadata -n filters 0` must match the §1 snapshot.
